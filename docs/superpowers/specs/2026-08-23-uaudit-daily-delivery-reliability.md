# UAudit: reliable daily iOS and Android delivery with safe queue recovery

Status: review-ready — implementation is blocked pending explicit approval.

Grounded repository state: `origin/develop` at
`99a14119d4f4cf7a9478b233d55d45e43bcab730` (2026-08-23).

## Goal

For each enabled iOS and Android daily routine, make its scheduled outcome
observable and recoverable without sacrificing the existing immutable binding,
Telegram receipt, lock metadata, or cursor compare-and-set guarantees. A
release-line transition, a no-commit day, a coalesced trigger, or a dead worker
must not silently look like a successful daily audit.

This change has two success criteria:

1. Each routine either delivers its normal audited result or a receipt-bound
   status for the scheduled slot; a no-change day is visible rather than being
   silently closed. Delivery remains honestly **at-least-once** until the
   provider exposes a verified idempotency key.
2. A stale generation can be recovered once, from the unchanged cursor, only
   after a fenced atomic claim has proved that it is not live and preserved its
   evidence. It must never be freed by deleting a lock or by a generic issue
   release.

## Confirmed diagnosis

The incident evidence available on 2026-08-23 showed the following pattern;
the deployment run must re-check it rather than treating it as live truth.

- The 2026-08-21 Android and iOS triggers were coalesced behind older active
  executions. Their canonical runs had already delivered, but the queued
  duplicate work did not make this obvious.
- Android's next run had `FROM == TO`. The dispatcher deliberately ends this
  case with a comment and no mutation, so no Telegram message is sent.
- iOS blocked after `version/0.50` disappeared: both dispatchers still require
  `FROM <= master <= strict-next`, while the resolver intended to handle release
  transitions is not installed or invoked by dispatch. The observed cursor was
  already at the next release head while `master` was behind it.
- `reconcile_uaudit_routines.py` can safely reconcile assignee/description
  drift, but does not attest trigger enabled state, cron, timezone, next slot,
  active generation, or delivery receipt. The generic watchdog is intentionally
  not a recovery analog: it can release a ghost issue lock and skips blocked
  issues, whereas UAudit has receipt and cursor evidence to preserve.

## Assumptions and invariants

- `uaudit-daily-android` and `uaudit-daily-ios` remain the stable routine
  identities. Existing cursor paths and metadata-bound versioned lock
  directories remain valid; this change does **not** weaken lock validation or
  rename live locks.
- A normal non-empty audit continues to use the existing delivery contract.
  A completed audit with zero findings already produces a Telegram message.
- A no-commit result is different from a zero-finding audit. It requires a
  separate slot-status receipt and must not create an audit run, advance the
  cursor, or write `cursor.done`.
- Git selection is fail-closed: an unproven, backwards, rewritten, skipped, or
  non-ancestral range is never converted to a no-change result.
- Production routines, schedule values, ownership, and active execution state
  are not trusted from repository defaults or the historic incident snapshot.
  The authenticated deployment preflight must prove them against the intended
  Paperclip company before any live recovery or trigger update.

## Delivery and recovery state model

The implementation must make these rules executable rather than infer them
from filenames or issue status.

- A canonical routine descriptor is generated from validated config and bound
  to a manifest digest. It contains `app_id`, stable `routine_key`, platform,
  cursor path, UTC-only cron, owner, and SLO values. The status helper accepts
  this descriptor, not caller-supplied app/routine values.
- A slot is derived from the verified Paperclip scheduled-execution timestamp
  and that descriptor's UTC cron; a retry/recovery carries the original slot.
  Manual invocations require a signed/hashed slot-proof generated by the
  supervisor. UTC is mandatory in this change, so DST has no ambiguous slot.
- The slot ledger has explicit states: `pending`, `deferred`, `audit_delivered`,
  `no_change_delivered`, `blocked`, and `delivery_uncertain`. Only
  `audit_delivered`, `no_change_delivered`, and `blocked` are terminal.
  `deferred` may transition to a normal audit/no-change/blocked result; it does
  not suppress a later valid audit for that slot.
- Before a status send, persist a `send_started` attempt with an attempt UUID.
  A confirmed provider response becomes the receipt. A timeout/crash after the
  provider may have accepted the send becomes `delivery_uncertain`, opens a
  Paperclip escalation, and retries under a bounded backoff policy. It may
  duplicate a Telegram message; the ledger reports that possibility rather
  than falsely claiming exactly-once delivery.
- Each routine declares an explicit production SLO: UTC cron, `delivery_slo`
  of 180 minutes, deferred notice after 60 minutes, and three status-delivery
  retries at 5, 20, and 60 minutes. These are proposed initial values and must
  match the authenticated live preflight before activation. A missed SLO opens
  one escalation and never makes the next slot appear green.
- A partial audit receipt is a third path: it awaits the existing digest-bound
  human approval for 24 hours. During that window the lease remains held and
  later slots are `deferred`. On expiry, the fenced controller atomically
  claims the exact partial generation, writes a
  `partial_approval_expired` quarantine record, renames its fenced lock, and
  performs the same revision/CAS-protected Paperclip release checks as any
  stale generation. Its cursor remains unchanged and the old partial result is
  never reconciled or discarded. The next scheduled slot may start one fresh
  daily generation from that unchanged cursor; its immutable profile must carry
  the prior partial receipt/quarantine digests as `supersedes_partial` evidence.
  This can re-review already reported commits, but cannot skip them or hide the
  expired partial. Approval received before expiry continues to use the normal
  digest-bound reconciliation flow.

## Scope

### 1. Make release selection executable and prove every range

- Add a manifest-bound, read-only CLI adapter for
  `uaudit_release_resolver.py`. It accepts only normalized direct-Git facts,
  emits a structured `Resolution`, performs no Git/network/state writes, and is
  installed and verified beside the existing delivery helper.
- Replace the inline release-selection prose in both platform dispatchers with
  one call to that verified CLI. The dispatcher collects direct refs and all
  ancestry facts, stores them in the hashed profile, and follows only the
  returned resolution.
- Extend the resolver decision table for the incident case: if the configured
  base is absent, only the strict successor is present, and `cursor ==
  successor_head`, resolve `no_change` even when `master` is behind the
  successor. This is safe because equality proves that there is no unreviewed
  successor delta; it is not an ancestry inference.
- Retain the existing strict-successor and recovery behavior for all other
  cases. In particular, only a proven ordered relation can form a daily range;
  no caller may construct a reversed or guessed `FROM..TO` range. A skipped
  release line remains an error.
- Define the adapter boundary for every resolver result. `daily`, `bridge`, and
  `transition` may bind the existing single `daily_delta` range only when their
  profile proves the segments form one contiguous, forward range; the profile
  retains the individual segment proof. `no_change` uses slot-status. `rebase`,
  `split_recovery`, and `full_recovery` use the existing forced-full/recovery
  path and cannot advance the daily cursor until a separately valid daily
  binding exists. No multi-segment result is left for a prompt to interpret.
- Install the resolver adapter and its manifest before deploying dispatcher
  bundles. The dispatcher checks the adapter's manifest version/digest before
  invoking it; a missing or incompatible adapter is a blocked status, not a
  shell fallback. Deployment rollback restores the mutually compatible helper,
  adapter, and bundles as one set.
- Keep the existing metadata-bound versioned lock convention. The helper
  already accepts a canonical `state/locks/*.lock` path only when its metadata
  and immutable binding match. Renaming or broadly relaxing it is unrelated to
  this incident and would add migration risk.

### 2. Deliver a daily outcome when there is no audit delta

- Add a distinct `daily-slot-status` contract to the delivery helper and the
  two InfraEngineer delivery roles. It validates a manifest-bound routine
  descriptor and supervisor-produced slot proof, records its attempt/receipt
  in the dedicated status ledger, and never calls `reconcile-daily` or writes
  an audit cursor.
- Supported status outcomes are `no_change`, `blocked`, and `deferred`. The
  message includes platform, scheduled slot, selected ref/head (when known),
  and a concise reason; it contains no credentials, mutable lock content, or
  unverified commit range.
- A normal delivered audit remains the terminal result for its slot. The new
  status path is used for no-change and for a safe failure/defer outcome. A
  deferred receipt is provisional, while blocked is terminal; both are bound
  to an attempt ID. Conflicting terminal results fail closed. A confirmed
  repeat is deduplicated locally, but an unknown provider result is surfaced as
  `delivery_uncertain` and may be retried at-least-once as defined above.
- Add a small slot ledger that links a normal audit delivery receipt or a
  status receipt to the scheduled routine slot. The ledger is evidence for the
  supervisor; it is not a second audit cursor.

### 3. Add UAudit-specific schedule and queue supervision

- Declare the expected daily trigger metadata (enabled state, UTC cron,
  ownership, and delivery SLO) in the UAudit routine configuration, validated
  as part of routine loading. The proposed initial values are Android `45 10 *
  * *`, iOS `0 11 * * *`, UTC, and the SLO values in the state model. They are
  intentionally fail-closed: the authenticated preflight must match them or
  implementation deployment stops before enabling control-plane reconciliation.
- Extend routine reconciliation with a read-only `--verify-live` health mode.
  It must prove exactly one live routine per configured stable key, expected
  ownership, enabled state, schedule fields, and the next/last execution facts.
  It produces a diff and exits non-zero on ambiguity, disabled triggers, or
  schedule drift. Existing description/assignee reconciliation stays
  revision-bound.
- Define a versioned `LiveRoutineSnapshot` adapter rather than reading arbitrary
  API JSON in the policy layer. Its required fields are authenticated company
  ID, routine UUID/revision, stable-key marker, enabled state, cron, timezone,
  owner, last/next scheduled execution time, and active execution ID/state.
  Missing, `null`, stale, or unrecognized fields are an error. Fixture
  envelopes document each supported Paperclip API shape and the capability
  probe identifies the exact revision precondition for a trigger patch.
- If the Paperclip API supports revision-safe trigger updates, make an explicit
  opt-in apply path for those exact fields and re-read to verify. If it does
  not, fail closed and emit a human remediation plan; do not claim that the
  current reconciler controls schedules.
- Implement a UAudit-specific supervisor in the watchdog service, with
  persisted per-slot/generation state and a bounded, fenced lease. It classifies a
  slot as delivered, fresh-active, coalesced-behind-live, terminal-without-
  receipt, or stale. It uses the generic watchdog only as a classification
  analog; it must not call generic `trigger_respawn` for UAudit generations.
- A worker renews its generation lease at bounded phase handoffs using the
  Paperclip response `Date` clock, a 15-minute TTL, and a 5-minute grace
  window. A fresh lease or a confirmed active Paperclip run is never stolen.
  API unavailability is `deferred`, never evidence of staleness. Coalesced work
  is linked only when routine key, original slot, and canonical generation ID
  match; otherwise it remains blocked for investigation.
- Recovery ownership is an atomic `O_CREAT|O_EXCL` record under the canonical
  shared UAudit state root, keyed by `(routine_key, slot, stale_generation_id)`.
  It includes a monotonically increasing fence token, lease/lock/profile
  digests, supervisor owner UUID, and state revision. Every worker phase and
  recovery mutation verifies its token. The controller atomically claims,
  re-reads active execution/lease/lock identity immediately before an effect,
  and aborts to quarantine on any mismatch. This deployment permits one
  supervisor authority per canonical state root; multi-host supervision is
  disabled unless an external compare-and-swap backend is added.

### 4. Recover the current queue safely after deployment

- Run the live-control preflight first. It must identify the intended company
  from authenticated configuration (never a placeholder), exactly two matching
  routines, their configured schedules/owners, current execution IDs, and the
  relevant cursor, lock, and receipt facts. Any mismatch blocks recovery.
- For a complete run with a valid delivery receipt, use only the existing
  receipt-led `reconcile-daily` flow. It may repair its terminal marker or
  confirm cursor state but must not send Telegram again. A `partial` receipt
  follows the bounded approval policy in the state model, never automatic
  reconciliation or automatic re-audit.
- For a fresh active run, retain the lock and observe its lease. For coalesced
  rows, close or link them only after proving their canonical live/terminal
  generation and slot receipt.
- For a terminal or expired generation without a receipt, atomically claim it,
  hash its immutable run artifacts/lock metadata/profile/lease into an indexed
  quarantine record, then atomically rename the fenced lock within the same
  state filesystem. Bind that record to the single recovery key and start at
  most one fresh generation from the unchanged cursor. The recovery performs
  release selection again; if a safe range still cannot be proven, it writes a
  receipt-bound `blocked`/`deferred` outcome instead of mutating the cursor.
- The recovery helper/controller must never manually edit cursor JSON, delete
  a lock, synthesize `workflow.done`, or replay a Telegram send. Direct
  Paperclip issue release is permitted only after the controller has recorded
  the exact stale execution identity, checked its revision/CAS precondition,
  and re-verified immediately before and after the effect that no new active
  execution appeared. Any TOCTOU mismatch aborts and quarantines; it never
  releases the newly active run.

## Non-scope

- No automatic selection of `version/X.(Y+2)` or of an arbitrary branch.
- No change to audit scope, reviewer chain, normal delivery payload semantics,
  or cursor CAS for non-empty audit runs. The existing partial-approval rule is
  retained; only its bounded supervision/escalation is added.
- No broad lock migration, deletion of historical evidence, or bulk cleanup of
  all Paperclip issues.
- No production queue mutation or schedule change in this spec-only change.
  Those are a separately logged post-deploy operation, gated by live preflight.

## Acceptance criteria

1. Both dispatchers invoke only the verified resolver adapter for release
   selection and contain no obsolete `FROM <= master <= next` hard requirement.
2. A missing base with strict successor head equal to the cursor becomes a
   receipt-bound `no_change` slot outcome, without creating an audit run or
   mutating its cursor. A skipped, reversed, or unproven case fails closed.
3. A confirmed repeated request for the same slot/status is locally deduplicated
   and a conflicting terminal status/head is rejected. A crash or timeout after
   a provider-accepted send is explicitly recorded as `delivery_uncertain`,
   alerted, and retried at-least-once; it never masquerades as exactly-once.
4. A complete zero-finding non-empty audit retains its existing normal Telegram
   delivery and cursor reconciliation, with no extra no-change status.
5. Live verification fails if it cannot prove exactly one enabled iOS and one
   enabled Android routine with the declared schedule, owner, and identity.
6. A fresh active lease is never released; a stale/terminal no-receipt
   generation is fenced, atomically claimed, quarantined with digests, and
   yields at most one recovery from the unchanged cursor. Concurrent controllers
   and a new execution appearing before release cannot bypass the fence. A
   complete valid receipt uses reconciliation, not recovery.
7. The supervisor identifies coalesced work as behind a canonical generation
   and does not start a duplicate audit.
8. A partial receipt without approval is retained and escalated until the
   configured deadline, then atomically fenced/quarantined/released with no
   cursor movement. The next scheduled slot may create one generation from the
   unchanged cursor only with `supersedes_partial` evidence; approval before
   expiry still uses the existing digest-bound flow.
9. Post-deploy recovery emits a verifiable terminal status or normal audit
   receipt for each recovered platform slot, with no manual cursor/lock edits.

## Independent review and decisions

Two independent read-only reviews were requested before this spec.

- The routine/analog review confirmed that receipt-led delivery/reconciliation
  is the primary reusable analog; it also identified the resolver/dispatcher
  disconnect and showed that generic watchdog release is unsafe for UAudit.
- The adversarial review found two critical defects in the first draft: local
  receipts cannot prove exactly-once after a provider-accepted crash, and a
  delivered `partial` without approval would still hold the queue forever. The
  revised design therefore promises at-least-once with an explicit uncertain
  state, and adds bounded partial-approval supervision without weakening human
  approval. It also added descriptor/slot validation, API snapshot capability
  gates, a full resolver-to-binding boundary, and atomic fence/CAS/TOCTOU rules
  for concurrent recovery.

One finding was deliberately *not* expanded into a change: versioned lock
paths are preserved. Current reconciliation already validates their canonical
parent, metadata, and binding, so weakening or renaming them would not address
the observed failures.

## Open questions

None for source design. The proposed initial UTC schedules and SLO are explicit
approval subjects above. The authenticated Paperclip preflight is still a hard
deployment condition: if it disagrees with config or lacks the declared
snapshot/patch capability, deployment/recovery stops and reports the
discrepancy rather than guessing.
