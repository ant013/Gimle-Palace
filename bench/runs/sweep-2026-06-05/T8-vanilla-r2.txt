## Silent-failure spot: Bitcoin send with insufficient UTXOs

**File:** `/Users/ant013/Ios/bench-vanilla/Unstoppable/Unstoppable/Modules/SendNew/BitcoinSendHandler.swift`

**Lines (baseline):** 39-43, inside `BitcoinSendHandler.sendData(transactionSettings:)`

### Where the silent failure happens

When the user's send amount equals their available balance, the handler tries to recompute `params.value` to the max spendable amount (so it adjusts for the fee):

```swift
if decimalValue == balance {
    params.value = adapter.convertToSatoshi(value: adapter.availableBalance(params: params))
}
```

`BitcoinBaseAdapter.availableBalance(params:)` (lines 299-302) is defined as:

```swift
func availableBalance(params: SendParameters) -> Decimal {
    let amount = (try? abstractKit.maxSpendableValue(params: params)) ?? 0
    return Decimal(amount) / coinRate
}
```

Note the `try?` — when the selected UTXOs cannot cover `amount + fee` (the classic "insufficient UTXOs" case), `maxSpendableValue` throws, and `availableBalance` silently returns `0`. The handler then sets `params.value = 0` and proceeds into `adapter.sendInfo(params:)`. The original "not enough" condition is swallowed: the user sees the form silently switch to a zero-amount send (or a confusing "ok" state with no error caution).

`UtxoSendHelper.caution(...)` already knows how to render `BitcoinCoreErrors.SendValueErrors.notEnough` as the localized "insufficient_balance" / "insufficient_balance.info" caution, so the smallest patch is to detect the zero-result branch and surface that error explicitly.

### Why this is the smallest fix

- Single file touched: `BitcoinSendHandler.swift`.
- Reuses the existing `BitcoinCoreErrors.SendValueErrors.notEnough` case, which `UtxoSendHelper.caution(transactionError:feeToken:)` already maps to the user-facing strings `"fee_settings.errors.insufficient_balance"` and `"fee_settings.errors.insufficient_balance.info"` (lines 33-37 of `UtxoSendHelper.swift`). No new localization keys, no new error types.
- The existing flow (`SendData.cautions(...)` -> `UtxoSendHelper.caution(...)`) propagates `transactionError` into a red caution, and `SendData.canSend` already returns `false` when `transactionError != nil`, so the Send button is correctly disabled.
- Wrapping the `sendInfo` block in `if transactionError == nil` avoids overwriting the surfaced `notEnough` with a downstream zero-amount error and avoids the extra RPC call.
